# Veil Warden：企業での限定試用に向けたビジョン

[現状と設計](ENTERPRISE_READINESS.md) / [タスク](ENTERPRISE_TASKS.md) / [段階](../milestones/enterprise/README.md)

2026-10-22。現在の能力と将来の仮説を分けた説明資料。
本番対応、監査認証、企業版の提供や発売時期を約束するものではない。

## 提供価値の仮説

指定したLinuxサービスの新規TCP接続を観測し、管理者が確認した宛先ルールで拒否・解除できれば、
アプリケーション内部へ監視コードを組み込まずに、外向き接続の調査と制御を補助できる。
対象のcgroup管理や導入設定は必要であり、任意のアプリ/コンテナへ無変更で適用できるとは限らない。
この価値が既存のsystemd制限、firewall、NetworkPolicyより役立つかは、対象利用者と検証する。

現時点の成果は、専用Linux VMの固定cgroupを対象とした研究用OSS。
TCP IPv4/IPv6の接続試行、事前のdeny tuple、手動解除、終了時の解除を限定環境で確認している。
許可イベントは接続成功や安全性を意味せず、データ流出の検知・防止を保証しない。
企業向けには、範囲を広げる前に導入・可観測性・停止復帰・成果物の検証を整える。

## 確認済みの設計上の配慮

- Rust、固定幅ABI、`repr(C)`、サイズ/offset検査、イベントデコード検証を用いる。
  これは特定の不整合を減らす設計で、unsafe・依存・kernel・VM基盤を含む安全性の完全証明ではない。
- enforceは明示的に選び、固定scopeと一致する新規TCP tupleだけを拒否する。
  正規の業務通信も、そのtupleに一致すれば拒否され得るため、影響確認が必要。
- RingBufの予約が失敗しても、計算済みの接続判断を維持する。enforce中のdenyを許可へ変えない。
  ログ欠落と接続制御の継続を別に記録する。
- プロセス終了に伴ってFD所有リンクを解放し、拒否が失われる現在の停止契約を明示する。
  これが停止時のfail-openであり、常時保護やzero-impactを意味しない。
- M5は明示した合成プロセス1件のargvを起動時に一度だけ評価する。
  生のargvや一致値を結果へ含めず、状態・既知ルール・件数を返す。検知から自動拒否しない。

M5の子プロセスは環境を引き継がず、dumpable無効、core上限0、CPU時間2秒、
仮想アドレス空間256 MiB、読取16 KiBと親側期限を設定する。
256 MiBはRSS実測ではなくaddress-space上限で、時間も厳密な終了保証ではない。
子プロセス分離は非特権化・seccomp/namespace sandboxの実装を意味しない。
生値のメモリ即時zeroize、swap/クラッシュ/他の監査経路を含む消去・非露出は保証していない。
現在のログ処理やTUIを非特権へ降格済みとも記載しない。

詳しい境界は [SECURITY.md](../SECURITY.md)、[SAFETY](SAFETY.md)、[M5仕様](SECRET_WARNING.md)を参照。

## 導入モデルの方向

初期候補は単体Linux上の一サービスで、observeから始める。
ビルド済みCLIと対応BPF objectを取得し、署名/identityと互換性を確認し、
非対話のログで対象と欠落を確認してから、必要な場合だけ制御へ進む。
packageのインストールだけで勝手にattach/enforceしない。

DaemonSetやHelmは将来候補。配置だけで全Podを監視できるとはしない。
Pod/cgroup寿命、対象ノード、対応kernel、必要権限、他agentとの共存、退避・解除を検証する。
数千ノードへの拡張性や性能は未測定で、現時点の提供能力には含めない。

bpffs保持やBPF program交換も候補であり、採用済みではない。
Map保持だけではlink寿命や観測ログの継続を保証しない。
現在の「停止で解除」と異なる契約になるため、独立した解除経路と復旧を実証してから選ぶ。
更新設計は [DEPLOYMENT](DEPLOYMENT.md) に集約し、漏洩ゼロ/無停止を先に宣言しない。

## 利用場面の採否

| 案 | 現時点の扱い | 追加で確かめること |
| --- | --- | --- |
| 一つの既存サービスの外向き接続調査 | 最初の候補。まずobserveと限定宛先の手動拒否・解除 | cgroupへの対象配置、管理/応答/依存通信、対象外維持、停止復帰。W0/W1/W2で需要と実装を確認 |
| CI runnerの依存取得先の制御 | 仮説として保留 | 現行はdenylistで、registry以外を全拒否するallowlistではない。DNS/CDN/可変IP、子process、既存socket、誤拒否と回避を別仕様・試験にする |
| 秘密を持つprocessの自動隔離 | 現計画に採用しない | M5はenviron/起動イベントの常時監視ではなく、警告と接続制御も非連動。初回漏洩防止や安全な自動隔離の根拠がない |
| レガシー全体のゼロトラスト化 | 本製品単独の達成目標にはしない | 認証・認可・運用・監査・対応プロトコル等の全体設計が必要。限定された新規TCP制御の補助と説明 |

実利用者・一サービス・一環境を選ぶことがW0。
今の主力プロダクトを止めるほどの価値がなければ、M5の成果を維持して追加実装を止める。

## 元の提案から採用しない表現

| 表現・主張 | 理由と代わりの説明 |
| --- | --- |
| 100% Memory Safe / Zero-Panic / 数学的に排除 | ABIと静的検査が確認する性質に限定。任意のkernel panicやメモリ破壊の不在は証明していない |
| Fail-Open / Zero-Impactを一括保証 | 停止時解除、イベント欠落時の判断維持、業務影響を分けて記載 |
| ゼロ・エクスポージャー / コンプライアンス違反を完全防止 | 結果へ生値を出さない設計と確認範囲を示す。メモリ完全消去や監査認証ではない |
| 全Podを自動保護 / 数千ノードへシームレス | K8sは未実装。対象選別・寿命・権限・性能の実証が必要 |
| パケット漏洩期間ゼロ | 現行は新規TCP connect制御。保持更新も未実装であり、全packet/ログ/既存通信の保証ではない |
| 起動時environ/argv検知から即自動遮断 | M5の対象・時点・警告のみという仕様と違う |
| ログ/TUIは非特権化済み | 現行のthread分離やスキャン子processは権限降格の証拠ではない |
| v0.1.0-alpha公開済み / Enterprise版を順次提供予定 | crate versionは0.1.0。公開tag/Releaseは今回未確認。商用版や提供日の合意もない |

M6の保留を「提供予定」へ言い換えない。
明確な範囲・失敗例・証拠・復旧手順が、企業で評価するための材料になる。
