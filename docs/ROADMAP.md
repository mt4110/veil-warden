# veil-warden ロードマップ

## 目的と成功条件

Linux のネットワークフックを Rust で扱い、観測から制御までの小さな縦の機能を完成させる。主力プロダクトを止める事業開発としては扱わず、週末の学習・研究枠とする。収益や需要は未検証であり、常駐型 DLP 製品へ自動的に拡張しない。

研究の問いは「Aya を使って、VM 内の限定されたプロセス群の接続先を観測し、事前ルールで新規接続を拒否できるか」。終了条件は M3 の VM 実験と復帰確認、または環境構築の時間枠超過。現在のプロダクトへの接続は未確認。veil-rs との再利用可能性は M5 で確認する。

## 最小のデモ手順

1. VM のローカル TCP 受信サーバーと専用テスト cgroup を準備する。
2. クライアントが cgroup に入ってからソケットを作り、IPv4 と IPv6 で接続する。
3. CLI で接続試行、宛先、PID/TID、取得できたプロセス名を確認する。
4. 特定の IP・ポート・プロトコルへの拒否ルールを、対象 cgroup の Map に事前登録する。
5. 新しい接続の拒否と、受信サーバー側で受信がないことを確認する。
6. 解除後の新規接続、対象外クライアント、SSH の維持を確認する。
7. 通常終了・強制終了後にリンクが外れ、接続が復帰することを確認する。

接続の成功・漏洩防止は、イベント表示だけで判定しない。クライアントの結果とサーバーの受信を合わせて見る。

## 継続と中止

- M0 が 3 時間で成立しなければ、VM/カーネル/ツールチェーンの阻害要因を記録してその週末は停止する。別の VM や OS を際限なく試さない。
- M2 が未完成なら M3/M4 に進まず、IPv6 を黙って対象外にして完成扱いにしない。
- 対象外通信への影響や終了後の遮断残留があれば、常駐化に進まない。
- M3 後は小さなデモを残して区切る。公開、販売、全プロセス監視は別の判断。
- 秘密検知による初回送信の防止を研究する場合は、接続前スキャンを行う明示的ランチャーやアプリ統合を比較する。argv のスキャンだけでも全秘密・全子プロセスの安全性は保証できない。研究の成功条件と時間枠を別途定義する。

## 実装前に確定する事項

M0 で VM 基盤、NixOS の版、Linux カーネル、Rust stable と検証ツールを記録・固定する。Aya/aya-ebpf、Rust nightly、bpf-linker は M1 着手時に対応する組み合わせを確認して固定する。NixOS を第一候補とするが、宣言的設定だけで VM ディスクや変更データが復元されるわけではない。スナップショットまたは再作成手順が必要。

M5 で veil-rs の実リポジトリ、利用 API、ライセンス、検知ルールとテストを確認する。現在はこれら未確認。モックの文字列検索を veil-rs 統合済みとは呼ばない。
