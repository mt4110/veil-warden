# veil-warden 安全性の根拠と限界

この文書の結論は「影響範囲を小さくし、失敗から戻れるようにする」です。100%安全を保証する設計ではありません。M0 は自作 BPF をアタッチせず、機能確認と合成通信を行います。

## Linux VM に限定する理由

eBPF のロード先はゲストの Linux kernel です。macOS / Darwin の kernel を変更する処理はありません。独立した VM にすることで、実験用のプロセス、cgroup、OS 設定をホストの日常作業から分離します。

ただし、hypervisor の未知の欠陥、共有設定の誤り、CPU/メモリ/ディスクの消費はホストにも影響し得ます。2 CPU・4 GiB のゲスト上限を設けますが、QEMU 自体のホスト側 overhead やダウンロード cache は別です。同時起動した2台の合計は最大8 GiBのゲストメモリです。

## ホストのデータを共有しない理由

専用 VM はホストのホーム、秘密鍵、認証設定、実トークン、作業ディレクトリをマウントしません。公開鍵ディレクトリのみを read-only で共有し、Nix の必要な closure は独立した read-only のイメージとして渡します。

構築用 VM は公式 bootstrap の既知ホスト鍵を使い、公開鍵・公開 CA 証明書・空の交換領域だけを共有します。必要なソースは選んだディレクトリだけを SSH でコピーします。Nix のホスト trusted-user 設定や `/etc` を変更しません。

ソースに実秘密を入れると Nix store や build archive に残り得るため、共有を絞るだけでは十分ではありません。合成データだけを使い、秘密をコード・文書・argv に入れないことも必要です。

## 接続を限定する理由

ホストからゲストへの転送は `127.0.0.1` の専用ポートに限定します。SSH の root・パスワード認証は無効です。専用 VM のホスト鍵は起動ごとに生成され、最初の loopback 接続で取得した鍵をその起動用に固定します。以降は StrictHostKeyChecking を有効にします。

最初の鍵取得は TOFU であり、同じホスト上の悪意ある利用者によるなりすましを防ぐ保証はありません。信頼できる単一利用者の Mac で使う条件です。ゲストコンソールの自動ログインとゲスト内 sudo は、VM 管理者がゲストを制御できることを前提にした操作性の選択です。

## cgroup を限定する理由

管理用 SSH は system.slice、合成クライアントは `/warden.slice/warden-test.slice` に置きます。M0 の機能確認では、クライアントの所属を確認してから新しくソケットを作り、IPv4/IPv6 loopback のサーバー受信まで確認します。

将来のフックも専用 slice に限定します。PID の取得は通信の意味やプロセス所有者の完全な証明ではなく、argv の秘密検知も送信の証拠ではありません。M3 の新規接続拒否で既存接続を止めることはできません。

## Verifier が担うこと

Verifier は BPF のメモリアクセス、初期化、制御フロー等を検査して、不正と判定したプログラムのロードを拒否します。Rust の no_std と固定 ABI の検査を加えることで、境界の誤りを減らします。

Verifier は設定した宛先ルールが利用者に適切か、誤検知がないか、イベントが欠落しないかを保証しません。kernel の欠陥がゼロだとも保証しません。[Linux Verifier の公式説明](https://docs.kernel.org/bpf/verifier.html)

## 復帰と停止

専用 VM の root は一時的な tmpfs で、writable Nix store もメモリ上です。正常に電源を切り、同じ固定イメージから再起動すると宣言した状態へ戻ります。ディスクを消して復元する必要はありません。再起動時に失われるゲスト内の変更はこの実験専用です。

構築用 VM のディスク、host cache、検証ログは保持します。削除や掃除は自動化していません。不要になった場合も対象・影響・復旧可否を確認してから扱います。

M1 以降では BPF link の寿命と終了を実測します。停止後に接続が戻る fail-open の研究用方針であり、常時保護される防壁ではありません。M0 の feature probe は一時的な BPF capability 試験を行いますが、自作の通信プログラムを cgroup に attach しません。

## 残る限界

VM 内でも、root 権限、cgroup 外の処理、既存・受け渡された socket、未対応プロトコルは境界の外です。TLS を復号しません。初回の秘密送信を阻止する機能、常駐の可用性、負荷下での通信性能は未実装・未検証です。

ガードと文書を維持しつつ、実カーネル・合成クライアント・受信側・停止後の復帰を確認することが、安全性を説明する根拠になります。
